# kotlin-calculator-precourse

## 서비스 소개
양수의 문자열을 구분자와 함꼐 입력받아 합을 구하는 문자열 덧셈 계산이 서비스입니다.

## 구현할 기능 목록

*   **[ ] View 구현:** 사용자와의 입출력을 담당하는 `View` 인터페이스와 `ConsoleView` 구현체를 작성한다.
*   **[ ] DelimiterAnalyser (구분자 분석기) 구현:** 입력 문자열을 분석하여, 숫자 부분과 구분자 정보를 담은 `ExpressionParts` 객체를 생성한다.
*   **[ ] NumberConverter (숫자 변환기) 구현:** `ExpressionParts`를 입력받아, 문자열을 검증하고 `Double` 숫자 목록으로 변환한다.
*   **[ ] Calculator (계산기) 구현:** `Double` 숫자 목록의 합계를 계산한다.
*   **[ ] Application (통합) 구현:** 구현된 `View`와 `Domain` 객체들을 조합하여 전체 애플리케이션의 동작을 관장한다.
*   **[ ] TestCode 구현:** 구현 완료된 서비스의 다양한 케이스를 테스트 하기 위한 코드를 추가한다.

## 고민과 결정

### 1. SRP는 어디까지 적용해야 할까?

*   **초기 설계:** `Parser`, `Validator`, `Converter` 등 모든 책임을 개별 클래스로 분리하여 SRP를 최대한 잘게 설계했다.
*   **문제 인식:** 하지만 이는 현재 과제 규모에 비해 클래스 수가 너무 많아지고, 오히려 구조 파악을 어렵게 만드는 오버엔지니어링이라고 판단했다.
*   **최종 설계:**  `DelimiterAnalyser`(구분자 추출+분석)와 `NumberConverter`(검증+숫자 변환)라는 두 개의 핵심 도메인 객체로 재구성함으로써, 원칙을 지키면서도 코드의 파편화를 막고 실용성을 높였다.

### 2. '양수'의 범위를 어떻게 정의할 것인가?

*   **고민:** 요구사항의 '양수'가 '양의 정수'에 국한되는지, '양의 실수'까지 확장될 수 있는지 명확히 정의해야 했다.
*   **결정:** **소수점을 포함하는 양의 실수(`Double`)까지 처리하도록 범위를 확장했다.**
*   **이유:** '양수'의 수학적 정의를 폭넓게 적용하여, '1.5,2.5'와 같은 다양한 입력까지 처리하는 더 유연하고 확장성 있는 프로그램을 구현하고자 했다.

### 3. '실수' 계산과 '정수' 출력의 딜레마

*   **고민:** 계산은 `Double` 타입으로 처리하지만, 요구사항의 출력 예시(`"1,2" -> 3`)는 모두 정수 형태이므로 이 둘 사이의 불일치를 해결해야 했다.
*   **결정:** 최종 출력 책임은 **`View`** 가 지도록 역할을 분리했다.
*   **이유:** '계산'의 책임은 `Domain`이, '표현(Presentation)'의 책임은 `View`가 갖는 것이 명확한 역할 분리 라고 생각했다. `View`는 전달받은 `Double` 값을 요구사항에 맞게, 소수점 이하가 0이면 정수 형태로, 아니면 실수 그대로 가공하여 출력한다.

### 4. 커스텀 구분자는 '추가'인가, '대체'인가?

*   **고민:** "기본 구분자 외에 커스텀 구분자를 지정할 수 있다"는 문장에서 '외에'의 의미를 명확히 해야 했다.
*   **결정:** 기본 구분자와 커스텀 구분자를 **모두 사용하는 '추가' 방식**으로 구현한다.
*   **이유:** 기본 구분자 사용 시 쉼표(`,`)와 콜론(`:`)을 함께 사용할 수 있었던 것처럼, 커스텀 구분자 또한 기존 구분자들과 함께 사용하는 것이 더 일관성 있다고 판단했다.

### 5. 커스텀 구분자로 허용되지 않는 문자가 있는가?

*   **고민:** 사용자가 `//1\n213`과 같이 커스텀 구분자로 숫자를 입력하거나, `//.\n1.2.3`과 같이 소수점 기호를 사용하는 경우를 방지해야 했다.
*   **결정:** 커스텀 구분자로 **숫자(0-9)나 소수점 기호(.)를 사용하는 것을 금지**하고, 위반 시 `IllegalArgumentException`을 발생시킨다.
*   **이유:** 명확성과 안정성을 위해 해당 문자들을 구분자로 사용하는 것을 금지했다.
